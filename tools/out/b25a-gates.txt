## 1. 为什么要补这一档

`328×723` 是批次 23-D 在真机（一加 Ace 6T）上量到的**这台机现在那一屏**：
ColorOS「显示大小」拉到最大 → `dumpsys` 里 Override density 620 → `1272/(620/160)≈328`，高 723。
它落 `@media (max-width:360px)` 的 `--fs-bucket:.9375` 一档，比 320 宽、比 390 窄。

改前状态：这一档只在 `tools/smoke-usable.js` 的几何腿里（`verify.js §37` 钉着 `[320, 328, 390, 452]`），
**像素侧零覆盖**。也就是说 README 里那句「真机 CSS 视口实测 328×723，328 那档在像素档外」
不是「覆盖了但没截图」，而是改版回归网从没有过这一屏 —— 断字、截断、拥挤这类只在窄屏出现的
症状，像素闸门一条都抓不到（25-B 的三条正是这一类）。

## 3. 三条既有条目 sha 变了 —— 如实登记，不写成「逐字节复现」

重拍后 `git diff tools/out/visual-baseline.json` 显示 3 条**与本次加档无关**的条目 sha 变化：
`topic.390x844`、`me.1440x900`、`md-manager.452x995`。

定性：与批次 24-F 基线之间的亚阈值像素抖动（对应 PNG 字节数 +88 或不变；不是代码改动，
本批产品文件零改动）。判据是**新基线自洽**：随后两遍全量只读，这 3 条逐条 `diff 0.00%`，
109 条里没有任何一条非零。所以「同一份代码连跑两次逐条 0.00%」成立，
而「重拍后与 24-F 基线逐字节相同」不成立 —— 后者本来也不是闸门要的东西（闸门比的是新基线）。

`tools/out/contact-sheet.js` 把 328×723 的 17 张基线最近邻缩放拼成

- 结论：这一档「拍得出、看得懂、抓得到真问题」，加档有效；上述三条改后要用同一张联络表复看。

## 5. 口径

- 加档的唯一合法路径：改 `VIEWPORTS` → 首跑必 `FAIL 基线文件不存在` → `--update` 全量重拍 → **两遍只读**才算数。
  只跑一遍不算：抖动只在复跑里现形（第 3 节那 3 条就是这么定性出来的）。
- 耗时基线从「92 态 ≈500s」抬到「109 态 470.6s 重拍 / 525–561s 只读」。加 17 张而总耗时没涨，
  是因为重拍与只读的前半程本来就在预热缓存；README 的活口径按实测写。
- 「109 态」是真值，任何文档里的态数必须由 `visual-baseline.json` 的 `count` 派生，不许手抄。
