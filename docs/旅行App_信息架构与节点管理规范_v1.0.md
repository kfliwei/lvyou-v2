# 旅行 App · 信息架构与节点管理规范

> 版本：v1.0  
> 核心原则：**地图是地点，路线是关系，美食是内容，Memory 是经历，Album 是故事。**

---

# 一、产品整体信息架构

每个省份拥有一个独立的「省级专题」。

```text
省级专题
│
├── 🗺 地图
├── 📍 节点
├── 🛣 路线
└── 🍜 美食
```

四个模块彼此独立，但可以共同参与旅行流程。

---

# 二、地图

## 2.1 地图的职责

地图只负责表达：

> **“这个地方在哪里？”**

地图上的对象全部必须具有地理坐标。

包括：

- 景点
- 古建筑
- 博物馆
- 古镇
- 自然景观
- 历史地点
- 拍照点
- 观景点
- 用户自行添加的地点
- 其他值得记录的地点

---

# 三、节点

Node 是地图中的核心实体。

## 3.1 Node 定义

```text
Node = 一个具有地理位置的旅行地点
```

每个 Node 至少包含：

```text
id
name
latitude
longitude
address
province
city
category
tags
description
coverImage
source
sourceId
createdAt
updatedAt
```

---

# 四、Node 类型

建议至少支持：

```text
SYSTEM
USER_CREATED
```

### SYSTEM

系统预置节点。

例如：

```text
岳麓山
岳麓书院
橘子洲
凤凰古城
张家界国家森林公园
```

### USER_CREATED

用户自己添加的节点。

例如：

```text
偶然发现的小茶馆
一个观景台
一条漂亮的小巷
拍照点
当地集市
```

---

# 五、Node 标签

标签不是 Node 类型，而是 Node 的属性。

例如：

```text
#必去
#网红
#古建
#历史
#自然
#博物馆
#古镇
#拍照
```

特殊标签：

```text
⭐ 必去
🔥 网红
```

但必须注意：

> 标签不能让地图变得五颜六色。

标签主要用于：

- 筛选
- 排序
- 强调
- 节点列表分类

---

# 六、Node 状态

建议支持：

```text
收藏
计划
去过
```

生命周期：

```text
收藏
 ↓
计划
 ↓
去过
 ↓
留下 Memory
```

---

# 七、7000+ 节点的地图显示原则

项目当前已经超过：

> **7000+ 节点**

因此地图不能采用：

```text
7000 个节点全部同时显示名称
```

而应该采用：

> **节点存在 ≠ 节点必须显示文字**

---

# 八、地图节点视觉层级

## 8.1 普通节点

```text
·
```

只显示极小点，不显示文字。

## 8.2 重要节点

```text
◉
```

可以根据重要程度略微放大。

## 8.3 当前焦点节点

```text
✦
```

显示名称，可以增加非常轻微的呼吸动画。

## 8.4 用户 Memory 节点

优先使用照片缩略图或简洁的 Memory 图标。

用户自己的记忆节点视觉优先级高于普通景点。

---

# 九、地图标签显示原则

默认：

> **地图不显示所有节点名称。**

只显示：

- 当前选中节点
- 搜索结果
- 当前地图中心附近的重要节点
- 标签匹配节点
- 少量高优先级节点

屏幕同时显示的文字标签建议控制在：

```text
8～15 个
```

避免地图出现大量文字互相覆盖。

---

# 十、标签避让

必须实现 Label Collision / Label Ranking。

节点优先级：

```text
当前选中
>
搜索结果
>
用户 Memory
>
必去
>
网红
>
重要景点
>
普通节点
```

当标签发生冲突时：

```text
优先级低的标签隐藏
```

而不是所有标签强行显示。

---

# 十一、标签筛选不是简单隐藏

例如用户选择：

```text
🌿 自然
```

不要：

```text
自然 → 显示
其他 → 删除
```

而应该：

```text
自然节点
→ 高亮

其他节点
→ 降低透明度
```

这样用户仍然知道当前区域还有其他地点。

---

# 十二、地图节点密度

建议提供：

```text
精简
标准
全部
```

### 精简

只显示：

- 重要节点
- 必去
- 网红
- 用户 Memory

### 标准

显示：

- 重要节点
- 普通节点
- Memory

### 全部

允许显示当前地图区域所有节点。

即使地图上有几百个节点，也允许用户主动选择全部。

---

# 十三、地图缩放与信息层级

地图 Zoom 不仅负责放大地图，还负责改变信息密度。

```text
远
↓
区域 / 城市

中
↓
重要节点 / Cluster

近
↓
具体景点

很近
↓
更多节点名称
```

原则：

> **地图缩放 = 信息层级变化**

---

# 十四、节点 Cluster

当节点密度过高时使用 Cluster。

例如：

```text
87
```

代表当前区域存在 87 个节点。

点击：

```text
87
↓
地图放大
↓
拆分成多个 Cluster
↓
继续放大
↓
最终显示具体节点
```

Cluster 保持数字 + 简单圆形即可。

---

# 十五、节点点击

点击 Node：

```text
地图保持当前位置
↓
底部出现 Bottom Sheet
```

示例：

```text
岳麓山

湖南 · 长沙

山水与书院相遇的地方

[ 🎧 听讲解 ] [ 🎙 语音记录 ]

        ＋ 加入行程
```

---

# 十六、节点核心操作

Node 详情至少包含：

```text
听讲解
语音记录
加入行程
```

其中听讲解、语音记录属于旅行体验；加入行程属于旅行工具。

因此视觉层级：

```text
听讲解    语音记录
       ↓
     加入行程
```

---

# 十七、节点管理

节点管理不是传统列表页面。

由于项目已有：

> **7000+ 节点**

因此节点管理必须使用：

> **空地图工作台**

---

# 十八、节点管理首页

进入「节点管理」默认打开干净地图。

不要一次加载全部 7000+ 节点。

地图根据当前 viewport 动态加载附近节点。

---

# 十九、节点管理入口

地图右下角：

```text
＋
```

点击：

```text
添加节点

🔍 搜索地点

📍 选择地图位置

⌖ 使用当前位置
```

---

# 二十、本地优先搜索

搜索必须采用：

```text
用户输入
↓
本地节点搜索
↓
有结果？
```

如果有，显示本地节点；如果没有，调用地图 POI 搜索。

---

# 二十一、搜索流程

```text
用户输入关键词
        ↓
本地 SQLite / FTS5
        ↓
     有结果？
      /    \\
    是      否
    ↓        ↓
本地节点   地图 POI
             ↓
          外部结果
             ↓
          去重处理
             ↓
          用户选择
             ↓
         添加为节点
```

---

# 二十二、搜索结果界面

建议分成两个区域：

```text
本地节点
────────────

岳麓山
湖南 · 长沙
✓ 已存在

岳麓书院
湖南 · 长沙
✓ 已存在

地图发现
────────────

某某茶馆
长沙市……

某某观景台
长沙市……

＋ 添加
```

这样用户能明确知道哪些已经存在，哪些是新发现。

---

# 二十三、重复节点检测

不能只依赖名称。

建议结合：

```text
名称相似度
+
坐标距离
+
POI sourceId
```

例如名称相似且距离 < 100m 时提示：

```text
附近已有相似节点

岳麓山
距离：43m

[查看已有]
[仍然添加]
```

---

# 二十四、地图 POI 与本地 Node 必须分离

数据层不要直接把地图搜索结果当 Node。

```text
Map POI
↓
候选地点
↓
用户确认
↓
TRACE Node
```

建议：

```text
source =
LOCAL
MAP_POI
USER_CREATED
```

---

# 二十五、搜索已有节点

如果搜索到本地节点：

```text
岳麓山

✓ 已在当前专题

[查看节点]
```

不能再次显示「＋ 添加」，防止产生重复节点。

---

# 二十六、从地图选点

支持「地图选点」。

进入后地图中心固定准星：

```text
           +
           │
      ─────┼─────
           │
           │
```

用户移动地图，底部显示：

```text
当前位置

附近已有节点：
岳麓山
距离 38m

[查看]
[创建新节点]
```

---

# 二十七、当前位置添加

用户可以直接：

```text
＋
↓
使用我的当前位置
```

自动获取 latitude / longitude，然后填写：

```text
名称
分类
标签
简介
```

快速保存。

---

# 二十八、添加节点不要设计成复杂表单

系统自动获取：

```text
名称
地址
坐标
省份
城市
POI 类型
```

用户填写：

```text
分类
标签
简介
我的备注
```

尽量不要让用户输入经纬度、地址、城市、省份。

---

# 二十九、快速添加

旅行途中应该支持：

```text
长按地图
↓
创建节点
↓
输入名称
↓
保存
```

其他内容之后再补。

原则：

> **先记录，再整理。**

节点列表中可以提供：

```text
全部

```

我的节点示例：

```text
◇ 老街里的茶馆
◇ 一个观景台
◇ 凤凰河边
```

系统节点：

```text
● 岳麓山
● 岳麓书院
● 橘子洲
```

# 三十一、节点管理操作

点击已有节点：

```text
编辑
```

如果节点已经存在 Memory：


# 三十二、区域统计

地图移动后：

```text
当前区域

128 个节点
23 个历史
18 个自然
12 个古建
8 个网红
```

点击「自然 18」，地图进入自然节点强调模式。

# 三十三、路线

路线是 Node 与 Node 之间的关系。

```text
Route
│
├── Node A
├── Node B
├── Node C
└── Node D
```

例如：

```text
岳麓山
↓
岳麓书院
↓
橘子洲
↓
太平街
```

路线负责：

> **怎么走**

---

# 三十四、加入行程

用户在 Node 中点击：

```text
＋ 加入行程
```

多个节点加入后：

```text
Node A
Node B
Node C
Node D
```

然后：

```text
生成行程
↓
排序
↓
发送到导航地图
```

---

# 三十五、美食

美食与 Node 完全独立。

重要原则：

> **美食不是 Node。**

不要把：

```text
剁椒鱼头
臭豆腐
小炒肉
米粉
```

当成地图节点。

---

# 三十六、美食的职责

美食负责：

> **介绍本省 / 本地区有什么值得了解和体验的食物。**

它是内容百科 / 文化内容，而不是地图 POI 数据。

---

# 三十七、美食数据模型

```text
Food
----------------
id
name
category
description
history
culture
taste
coverImage
gallery
tags
createdAt
updatedAt
```

不强制要求 latitude / longitude。

---

# 三十八、美食 UI

美食应该使用：

> 杂志 / 编辑精选式 UI

而不是地图 UI。

例如：

```text
经典湘菜

┌─────────────────────┐
│                     │
│       图片           │
│                     │
└─────────────────────┘

剁椒鱼头

酸、辣、鲜、香

湖南最具代表性的湘菜之一
```

---

# 三十九、不要强行建立 Food → Node 关系

允许：

```text
Province
↓
Food
```

但不要求：

```text
Food
↓
Node
```

美食和景点是两个独立内容体系。

---

# 四十、Memory

Memory 是：

> **用户亲身经历产生的旅行记忆。**

它可以关联 Node。

```text
Memory
│
├── nodeId
├── audio
├── transcript
├── story
├── photos
├── location
└── timestamp
```

---

# 四十一、Memory 与 Food

不要强制 Memory → Food。

用户当然可以在游记里提到某种美食，但这属于用户故事内容，不是数据模型上的强绑定。

---

# 四十二、Trip

Trip 是一次完整旅行。

```text
Trip
│
├── Nodes
├── Route
├── Memories
├── Photos
└── Album
```

---

# 四十三、Album

Album 是旅行的最终故事表达。

```text
Trip
 ↓
Memories
 ↓
Photos
 ↓
Route
 ↓
AI 编排
 ↓
Album
```

---

# 四十四、完整数据关系

```text
Province Topic
│
├── Nodes
│    │
│    └────────────┐
│                 ↓
├── Routes       Trip
│                 │
│                 ├── Route
│                 ├── Memory
│                 ├── Photo
│                 └── Album
│
└── Foods
```

其中：

```text
Nodes = 地点
Routes = 地点之间的关系
Foods = 独立内容
Trip = 一次旅行
Memory = 我的经历
Album = 最终故事
```

---

# 四十五、产品核心哲学

整个 App 不应该被理解成一个景点地图，而应该是：

```text
世界
 ↓
地点
 ↓
我选择的地点
 ↓
我的旅行
 ↓
我的记忆
 ↓
我的故事
```

地图负责：

> **发现世界**

节点负责：

> **管理地点**

路线负责：

> **组织旅行**

美食负责：

> **了解地方文化**

Memory 负责：

> **保存经历**

Album 负责：

> **重新讲述旅行**

# 四十七、最终原则

### 地图

> 不追求显示所有信息，而追求空间关系。

### Node

> 不追求复杂，而追求准确的地点数据。

### Route

> 不存内容，只表达地点之间的旅行关系。

### Food

> 不进入地图，专注地方文化与美食介绍。

### Memory

> 不追求标准化，保存用户真实经历。

### Album

> 不追求数据展示，而是把旅行重新变成故事。
