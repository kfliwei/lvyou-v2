# APK 产物命名与构建口径（两台机器统一标准）

日期：2026-10-06　适用：本机（Windows / `F:\MyAi\trace`）与另一台开发机（`C:\Users\kfliwei\…`）

## 0. 为什么要出这份标准

同一版前端，两台机器打出来的产物文件名不一样：

| 机器 | 实测产物名 | 分隔符 | 变体后缀 | 构建工程 |
|---|---|---|---|---|
| 本机 | `行迹TRACE_v2.26.10_debug.apk` | 下划线 `_` | `debug` | 外部壳 `F:\MyAi\trace\lvyou-v2-android` |
| 另一台 | `行迹TRACE-v2.26.9-release.apk` | 连字符 `-` | `release` | 仓库内 `lvyou-v2/android_app` |

名字不同只是表象，背后是**三处真实的分叉**：构建目标不同、变体不同、版本号来源不同。其中「变体写成 release 而实际签的是 debug 键」和「两台版本号各自漂移」这两条会直接影响能不能覆盖安装，所以必须一次定死口径。

## 1. 三条根因（全部实测，带 file:line）

### 1.1 名字是人工 `cp` 起的，gradle 不参与命名

两侧 `app/build.gradle` 里都**没有** `outputFileName` / `archivesBaseName` / `applicationVariants` 任何一条重命名配置（`grep` 在 `android_app/` 只命中 `signingConfigs` 与 `signingConfig` 两处，壳侧 50 行 build.gradle 全文同理）。
所以 gradle 的原始产物**永远**叫：

- `app/build/outputs/apk/debug/app-debug.apk`
- `app/build/outputs/apk/release/app-release.apk`

「行迹TRACE」那一段是打包人 `cp` 时自己拼的 ⇒ **两台各写一套习惯，编译器不会拦**。这是本条问题能长期存在的唯一原因。

### 1.2 那台读的是 `android_app/`，本机读的是外部壳 ⇒ 版本号天然漂移

| 位置 | versionCode / versionName（实测行号） |
|---|---|
| `lvyou-v2-android/app/build.gradle:22-23` | `49` / `'2.26.10'` |
| `lvyou-v2/android_app/app/build.gradle:19-20` | `48` / `'2.26.9'` |

`android_app/` 自 2026-10-04 起定位是**壳侧源码的入库副本，不是构建目标**。它那份 build.gradle 是故意没被覆盖的（仓库侧多出 `keystore.properties` 的 release 签名逻辑，壳侧没有）。**那台 `-v2.26.9-release` 里的 `2.26.9` 就是从这个 48 档读出来的**，不是它自己算错。

`交接报告-2026-10-03.md:102` 登记的命令仍是那台的跑法：`cd android_app && … gradle.bat assembleRelease`。**那一行现在是错的口径**，见 §4。

### 1.3 名字叫 release，签的却是 debug 键（本机侧）

- 外部壳 `lvyou-v2-android/app/build.gradle:26-35`：`release` 和 `debug` **两个 buildType 都写 `signingConfig signingConfigs.debug`**，`storeFile file('debug.keystore')`（这个 keystore 不入库）。
- 仓库内 `lvyou-v2/android_app/app/build.gradle:5-9 / 23-36`：`release` 走 `signingConfigs.release`，读 `keystore.properties`；**该文件不存在时回退 `release.keystore` 且口令取空串默认值**——即那台如果本地没有 `keystore.properties`，`assembleRelease` 要么失败，要么用一个静默的默认键。

结论：**文件名里的 `_debug` / `-release` 在两台侧都不等于签名身份**。用它来标"这是什么包"是错的，签名身份只能靠 `apksigner verify --print-certs` 读。

## 2. 标准（唯一口径，两台照此执行）

### 2.1 命名模板

```
行迹TRACE_v<versionName>_<variant>_<machine>.apk
```

- 字段分隔一律**下划线 `_`**，禁止连字符（连字符在 shell/URL 里易被当减号，且历史 13 支全是下划线，向存量靠拢）。
- `<versionName>` **必须从 build.gradle 实读**（`grep versionName app/build.gradle`），不许照记忆或照 commit message 手写。
- `<variant>` 只允许 `debug`；`release` 在未接入正式签名前**禁止使用**（§1.3：现在写了是误导）。
- `<machine>` 新增字段，取值 `win-a`（本机）/ `win-b`（另一台）。这是唯一能防跨机覆盖装不上的可见标记。

例：`行迹TRACE_v2.26.10_debug_win-a.apk`（本机 49 这支改名后即此名）。
存放位置：`lvyou-v2/APK/`（`.gitignore:2` 已忽略，不入库）。

### 2.2 构建目标与命令（两台必须一致）

- 构建目标**只有**外部壳 `lvyou-v2-android`；`android_app/` 只用于跨机 `diff -r` 量落后多少。
- 变体只有 `assembleDebug`。
- 出包前必跑 res 预检 `node tools/out/probe-shell-res.js`，exit 0 才交给 gradle。
- 每次出包前先 `grep -n 'versionCode\|versionName' app/build.gradle` 确认版本档，再升，再打。

### 2.3 出包后四条核验（缺一不算交付）

1. `aapt2 dump badging` → `versionCode` / `versionName` 与文件名两个字段**逐字相等**（用 D:/Android/Sdk/build-tools/36.0.0/`aapt2.exe`，注意是 `.exe` 不是 `.bat`）。
2. `apksigner.bat verify --print-certs` → 记下 SHA-256 摘要**写进文件名无法表达的那张表**（本机 `b696e89a…`，另一台 `6b4fba7a…`，实测两台 debug 键不同）。跑它要 `export JAVA_HOME="D:/jdk/jdk-17.0.14+7"`（只有 .bat）。
3. **必须 `unzip -p` 解条再搜**，不许对 APK 原始字节 `includes`——assets/dex 是 deflate 的，直接搜会把在包里的全部报「缺」。核验项：`assets/sw.js` 的 `CACHE='trace-vNNN'`、本批关键件、品牌字字节数。
4. `unzip -l` 数包内 assets，与壳内 `find` 逐名 `comm` 对账。已知稳定差额：aapt 不收录以 `.` 开头的目录（实测 7 个 `assets/data/.cache/run-*/json`）；**包内多 0** 才算过。

### 2.4 versionCode 分档（跨机不撞车的硬规则）

两台 debug 签名不同 ⇒ **同 versionCode 互相装不上**，而"先卸载再装"会连带清掉 WebView 的 IndexedDB / localStorage（游记、图册、心愿单全在里面，没 WebDAV 备份就是真丢数据）。

- 本机占**奇数**档（当前 49），另一台占**偶数**档（下一支从 **50** 起）。
- 长期解法是人工把同一个 `app/debug.keystore` 同步到两台（**不要提交进 git**）；做到之前，分档规则必须守。
