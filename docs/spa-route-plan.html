SPA 路由改造：约束分析与技术路径

背景：App 以 file:// 多页静态架构运行（WebView 壳）。本轮已落地"页面体验层"（全局过渡动画、返回栈统一、启动遮罩）；以下为全量 SPA 的约束与可行路径。

核心约束

约束file:// 下无法 fetch 局部页面浏览器对 file:// 的 fetch 请求默认按跨域拦截（此前冒烟测试已实测：manifest 都被 CORS 拦截）。SPA 的核心机制"按需加载页面片段"因此不可用——除非：
① WebView 壳开启 setAllowFileAccessFromFileURLs(true)（Android WebView 允许同目录 file fetch）；或
② 构建期把所有页面合并进单个 HTML（13 个页面 × 平均 40KB = 约 500KB 单文件，可接受但后续维护需构建工具）。

三条可选路径

路径做法收益成本/风险建议
A · 壳层开启 file fetchMainActivity 加 setAllowFileAccessFromFileURLs(true) + 页面侧引入 app-router.js（hash 路由 + fetch 局部渲染 + 返回栈）真 SPA：切换不白屏、返回栈精确、页面状态保持壳改 1 行 + 每页接入路由钩子（13 页 × 半天）；开启 file fetch 有轻微本地文件读取面（自用 App 风险可忽略）推荐，上架前验证
B · 构建期合并单文件写 build 脚本：13 页 HTML 模板化合并 → 单 index.html + hash 路由切换 section纯前端方案，不依赖壳每页内联 script 作用域隔离要处理（IIFE 包装）；后续每次改页要跑构建；调试变复杂备选，适合未来上架
C · 体验层（已落地）全局页面过渡动画 + 启动遮罩 + 返回栈统一 + 数据懒加载体感提升 80%（白屏被遮罩过渡掩盖、切换有动效），零架构风险已实施，无成本当前基线

路径 A 的实施清单（待做）

1. 壳层（Android）：MainActivity 的 WebSettings 加 setAllowFileAccessFromFileURLs(true)（targetSdk 34 默认 false）。 2. app-router.js：hash 路由（#/topic?p=bj）→ 预取下一页面 HTML（fetch → innerHTML 注入容器）→ 执行页面脚本（需每页 IIFE 化 + 依赖脚本全局加载一次）。 3. 页面接入：13 个页面把 <body> 内容与内联脚本抽为"页面模块"，注册进路由表。 4. 依赖治理：公共脚本（leaflet/travel-notes/topic-common 等）改为路由层加载一次，不再每页重复注入。 5. 回归：全量冒烟（现有 smoke 套件可复用）。
结论：本轮保持 C（体验层），上架/正式发布前走 A（壳层 1 行 + 路由模块化），预计 2-3 天工作量。
