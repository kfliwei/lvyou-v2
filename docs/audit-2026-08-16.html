结论先行

这是一个方向清醒、且确实在持续收敛的纯前端项目：上一轮审核的多数 P0 功能 bug 已修复，window.Ai / window.Geo 两大公共入口也已收口。工程兜底意识仍在。

但本轮发现一个比「代码重复」更伤用户的问题——四个已开发完成的成果功能（纪念册 / 图鉴 / 路书 / 故事）在全部页面里找不到任何入口，成为「孤儿功能」。普通用户要么根本不知道它们存在，要么知道也点不到。

其余问题集中在三类：① 公共逻辑与样式仍大面积复制粘贴（esc ×12、haversine ×6、双 :root、通用组件每页重写）；② 冗余数据与死代码未清理（3MB 僵尸文件、零引用路由框架、双份注册表）；③ 面向普通用户的认知门槛偏高（核心 AI 能力依赖用户自备 DeepSeek Key、设置页暴露开发者黑话）。

一、代码架构问题 Architecture

按严重度分三级：A = 功能断裂/死代码（用户可直接感知）· B = 重复未收口（维护风险）· C = 工程卫生。

A · 功能断裂

成果工坊四个功能已无任何入口 —— 孤儿代码

README 宣称的「成果工坊」包含旅行纪念册 / 个人图鉴 / 定制路书 / 旅程故事，对应 results.js 暴露的 Results.album / atlas / itinerary / story 四个函数，实现完整（含筛选面板、AI 叙事、文档导出）。

但全项目检索这四个函数的调用点，结果为零。唯一的入口 Results.open() 直接 location.href='review.html'，而 review.html 里只有「年度报告 / 横版海报 / 足迹海报 / 制图海报」——没有这四个功能的任何按钮。

证据：grep Results.(album|atlas|itinerary|story) 全项目命中 0；review.html 仅 aiReport / posterBtn / posterBtnH / posterCarto 四个动作。 建议：在「回顾」页或「我的」页增设「成果工坊」分组，把四个入口接回；或在 review.html 顶部加一个「生成纪念册 / 图鉴 / 路书 / 故事」的工具条。这是当前成本最低、收益最高的一件事。
A · 死代码

app-router.js 零引用，SPA 方案未落地

app-router.js 是一个完整的 SPA 路由框架（fetch 片段 + 脚本执行 + 返回栈），但没有任何页面 <script> 引入它，也没有任何 Router.register/go 调用。所有页面仍走整页 location.href 跳转。

证据：grep app-router.js|Router.register|Router.go 仅命中自身注释。 建议：若决定继续整页跳转（当前做法对无框架项目其实更稳），直接删除该文件并移除 docs/spa-route-plan.html 相关计划，避免误导后续维护者。
B · 重复

esc() 重复 12 处且语义不一致，XSS 面未完全收口

HTML 转义函数在 12 个文件里各自定义：travel-notes.js / results.js 转义引号，而 search.html / review.html / story.html / travel-map.html / wishlist.html / topic-common.js 等不转义引号。自定义节点 label/desc（用户输入 + AI 输出）进入 innerHTML 拼接时仍有注入缺口。

证据：grep "function esc(" 命中 12 处；search.html:103 只替换 &<>。 建议：抽一个全局 window.UI.esc()（含引号全转义），逐页替换本地实现，重点套到自定义节点渲染链路上。
B · 重复

haversine 距离仍重复 6 份，其中一处缺钳制

geo.js 已收敛为主入口，但 poster.js / results.js / wishlist.js / review.html / wishlist.html 仍各留一份内联实现。review.html:173 的版本缺 Math.min(1,·) 钳制，近对跖点会产出 NaN，污染「里程」统计。

证据：grep "6371" 命中 6 文件。 建议：统一改调 window.Geo.hav()，顺手修掉 review 的 NaN 隐患。
B · 令牌

design.css 双 :root，设计令牌无单一事实源

design.css 存在两个 :root（第 15 行与第 1127 行），后者二次覆盖 --fs-*（14px→0.9375rem）与 --radius-md 等，是圆角/字号跨组件漂移的直接根源。加上 map.css 与 design.css 双份大 CSS 并存，样式来源越发难追。

证据：design.css:15 与 :1127 两个 :root；:1127-1132 覆盖 --fs-*。
B · 组件

通用组件样式每页复制粘贴（topbar / back / bottom-nav）

顶栏、返回键、底栏五 Tab 的 CSS 在 index / me / settings / explore-map / search / wishlist / review / planner 等页各自重写一份几乎相同的样式，且细节已开始分叉（back 按钮 34px / 40px / 44px 三种尺寸并存）。改一个组件要同步 8 个文件。

证据：各页 <style> 内均有独立 .topbar / .t-row .back / .bottom-nav 定义。 建议：把 topbar / back / bottom-nav / toast 收敛进 design.css 的公共类，页面只保留业务样式。
B · 冗余

nation-data.js（3MB）已成僵尸文件

nation-data.js（3.04MB）在注册表里仍是「全国」专题的 dataJs，但 topic.html:154 已用 if (dataJs==='nation-data.js') loadNationIndex() 拦截，实际加载的是 662KB 的 nation-index.js。3MB 文件不再被加载，却仍在仓库与 APK 资产里占体积。

证据：ls 显示 nation-data.js 3,040,835 B；nation-index.js 662,984 B。 建议：删除 nation-data.js 并同步更新注册表 dataJs 字段，APK 体积立减约 2.4MB。
B · 冗余

topic-meta.js 与 topic-meta-lite.js 双份注册表并存

topic.html 加载 119KB 完整版 topic-meta.js，search.html 加载 56KB 精简版 topic-meta-lite.js。两份数据同源却需手动同步（主题色/别名改动要改两处），已出现字段漂移风险。

证据：两文件 window.TOPIC_REGISTRY 结构重复。
C · 卫生

tools/ 堆积 200+ 一次性脚本，无正式测试框架

tools/ 目录有 fix-*/check-*/diag-*/probe-*/patch-* 等 200 余个一次性脚本，记录了开发过程中的大量打补丁操作。它们不是测试、无法回归，长期看只会干扰对新工程师的理解。

证据：ls tools/ | wc -l 远超 200。 建议：把仍在用的 verify/smoke/gen-* 保留，其余归档或删除；用 tools/verify.js 作为唯一入口统一验证。
C · 健壮性

内联 onclick 依赖 window 全局挂载，易静默失效

多个页面用 onclick="doCheckin(i)" 内联调用，函数必须显式挂到 window 才有效（wishlist.html 甚至专门写了注释「必须挂 window，否则点击 ReferenceError 无响应」）。任何一次重命名或作用域调整都会让按钮「点了没反应」。

证据：wishlist.html:522-525 手动 window.doCheckin = doCheckin。 建议：改事件委托（addEventListener）或统一 data-action 分发，去掉全局泄漏。

二、普通用户视角 User Experience

站在一个「不太懂技术、只想记录旅行」的用户角度，看功能是否合理、操作是否友好。

高频痛点

「海报与年报」按钮落点与文案不符

首页底部主按钮写着「海报与年报」，点击后 Results.open() 跳到 review.html（「旅程回顾」页）。用户预期看到海报生成，实际进入的是一个统计/日历/成就页面，需要自己再找海报按钮。文案与落点对不上，是一处「点完一愣」的体验。

建议：按钮改叫「旅程回顾」直接对应页面；或让首页按钮直达 review 页的「足迹海报」区。
高频痛点

核心 AI 能力依赖用户自备 DeepSeek Key，门槛偏高

「AI 润色」「年度报告」「旅程故事」「定制路书」是产品的核心卖点，但全部依赖用户在设置页手动填入一个 sk-... 的 DeepSeek API Key。对普通用户而言：不知道 DeepSeek 是什么、不知道去哪申请、不知道怎么填、填错没反馈。结果大概率是——核心卖点在普通用户手里永远用不上。

证据：results.js:23 未配 Key 时提示「请到 设置 → AI 润色 填入 DeepSeek key」。 建议（任选）：① 内置一个默认中转/限流 Key（需后端）；② 提供「一键申请」引导页，把申请链接、粘贴位、测试按钮做成三步向导；③ 至少明确「不填 Key 也能用全部本地功能」并给一个可见的降级提示，而不是点生成时才弹错误。
信息架构

底栏「探索」与「专题」两个 Tab 内容高度重叠

底栏第一个 Tab「探索」是 index.html（杂志首页，含专题列表 + 时令推荐），第二个 Tab「专题」是 explore-map.html（专题地图列表）。两者在用户眼里都是「选一个地方去看」，首页也列了 8 个专题卡片、探索页又列了 30+ 个，功能定位重叠，用户分不清该点哪个。

证据：index.html 的「附近，有什么故事」8 张专题卡 vs explore-map.html 的 30 张专题卡，内容同源。 建议：明确分工——首页只做「情绪入口 + 时令 + 最近旅程」，把「所有专题地图」统一交给「专题」Tab；首页专题卡片精简为 3–4 张并注明「更多见专题」。
认知负担

设置页「高级设置」暴露开发者黑话

即使已折叠进「高级设置」，里面仍堆着「节点分级 / 聚合密度 / 必去优先 / 高德 Key / 管理 MD 库 / 补全地点信息 / 导出 Obsidian 库」等术语。普通用户点开只会更困惑，也容易误点「载入示例数据」「清除全部数据」这类有副作用项。

证据：settings.html:127-187 高级设置 7 个条目。 建议：把「高级设置」拆成「地图调节（3 项）」与「开发者/数据迁移（隐藏更深或长按进入）」两级，普通用户默认只见前者。
预期管理

网页版语音记录不可用，但引导未明确告知

核心功能「语音随手记」依赖 App 壳内的讯飞/Google 识别，网页版仅有 Web Speech 降级（浏览器兼容性差、且多数桌面浏览器不支持中文识别）。但首启引导和首页 CTA 都在强调「语音记录」，网页用户点了可能「没反应或识别失败」，产生挫败感。

证据：settings.html:260 诊断信息写「当前非 App 环境：无原生语音引擎」。 建议：网页环境首次点击语音时给一个明确提示「语音识别在 App 内体验最佳，网页版可手动输入」，并提供手动输入兜底入口。
可访问性

触控目标普遍 < 44px，深色残留

返回键 34–40px、日历翻月键、标签 8px 等高频热区小于 iOS/Android 建议的 44px 最小值；results.js 的生成弹窗与导出的 HTML 文档仍硬编码浅色（#FAF8F3 / #fff / #20201D），深色模式下会突然切回刺眼白底。

证据：settings.html:16 back 34px；results.js:34/202/340 多处内联 #FAF8F3。 建议：高频热区用透明 padding 抬到 44px；结果弹窗与导出文档接入 var(--color-*) 令牌。

三、优先级建议 Priority

按「用户价值 ÷ 改动成本」排序，前三条建议先做。

把成果工坊四个入口接回
在「回顾」页或「我的」页加一组「纪念册 / 图鉴 / 路书 / 故事」入口，调用现成的 Results.album/atlas/itinerary/story。功能已写完，只差一个入口——纯 UI 接线，价值最高。
清理死代码与僵尸数据
删除 app-router.js、3MB 的 nation-data.js（及注册表引用）、重复的 topic-meta 一份；APK 立减约 2.4MB，仓库更清爽。
收口 esc / haversine / 通用组件样式
抽全局 UI.esc() 与统一调 Geo.hav()，把 topbar/bottom-nav 样式收敛进 design.css。一次性消除 12 处 esc、6 处距离、8 份组件样式的漂移与 XSS 面。
降低 AI 门槛 + 修正文案落点
给 DeepSeek Key 做「一键申请」向导或默认降级提示；首页「海报与年报」按钮改名「旅程回顾」。直接改善新用户首体验。
信息架构梳理 + 深色/触控打磨
厘清「探索 / 专题」两个 Tab 分工；设置页高级项两级折叠；高频热区抬到 44px；results.js 弹窗接入深色令牌。属持续打磨项。
